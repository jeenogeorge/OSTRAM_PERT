OSTRAM, OSeMOSYS for Transmission – Framework to represent power systems connectivity, builds on OSeMOSYS and OSeMOSYS Global. It adds detail on internal transmission and on the interconnectors between countries, and supports "what if" comparisons between scenarios. The South Asia model is its reference application. The solvers GLPK, CBC, CPLEX and Gurobi are supported.

Developed by Climate Lead Group.

Installation

Supported environment

OSTRAM requires Python 3.10 or newer, conda, Git and a solver. The conda environment is defined in environment.yaml, and the Python package requirements are also declared in pyproject.toml. The steps below are for Windows PowerShell. Terms are in the glossary.

Install

  1. Install Git and Miniforge, a conda installer that uses only the conda-forge channel. Download Miniforge from https://conda-forge.org/download/ and keep the default options. Open the Miniforge Prompt from the Start menu, run conda init powershell once, and close it.

    If PowerShell later reports that running scripts is disabled, run Set-ExecutionPolicy -Scope CurrentUser RemoteSigned once in PowerShell.

    Open a new PowerShell window. conda --version and conda env list work there. Run every command on this page in that window.

    If you already use Miniconda or Anaconda and conda env create stops with a message about Anaconda's terms of service, install Miniforge, or accept those terms if your organisation's licence covers it.

  2. Clone into a short path, such as a folder directly under the root of a drive. Some output paths of the scenario A_Calibrated_BAU_Clipped_TxFreeze2026 come close to the Windows path limit, and a long clone path makes them fail.

    git clone https://github.com/Climate-Lead-Group/OSTRAM.git OSTRAM
cd OSTRAM

  3. Create the environment and install the package in editable mode. The editable install makes ostram importable from any folder while the inputs and the configuration stay in the clone.

    conda env create -f environment.yaml

    The environment is named OSTRAM-env, the name in environment.yaml. The channel list comes from environment.yaml, which names conda-forge, and from your own conda settings. Conda prints Channels: conda-forge, defaults when your settings add defaults. Conda 24.11 does not accept --override-channels with conda env create -f. To see the list, run conda config --show channels.

    If this command fails, stop. Every later command needs the environment.

    conda activate OSTRAM-env
python -c "import sys; print(sys.prefix)"
python -m pip install -e .
python -m pip check

    The printed path ends with envs\OSTRAM-env.

    An environment is broken when its folder has no python.exe. conda env list shows the folder of each environment. Remove a broken OSTRAM-env and create it again:

    conda env remove -n OSTRAM-env
conda env create -f environment.yaml

  4. Set the encoding and check the installation. Set PYTHONUTF8 again in every new window before a pipeline command.

    $env:PYTHONUTF8 = '1'
python -m ostram --help
python -m ostram inspect-resources
glpsol --version
cbc -stop

  5. Run the install check. The full list of solver-free checks is under Tests in CONTRIBUTING.md.

    python -B -m unittest discover -s tests -p "test_*.py"

python -m ostram run checks the environment named in environment.yaml, OSTRAM-env, and creates it when it is missing. Pass --env-name <name> to every run only when you created the environment under another name. Every stage runs under the Python that called the command, so run the commands from the activated environment.

For an existing environment, update it with:

conda env update -n OSTRAM-env -f environment.yaml --prune
python -m pip install -e .

How the command finds conda

python -m ostram run calls conda to check the environment. It takes conda from CONDA_EXE when that variable names an existing file; conda sets it in every activated prompt. Otherwise it takes the first of conda.exe, conda and conda.bat found on PATH. A .bat or .cmd hit, such as condabin\conda.bat of a standard install, resolves to Scripts\conda.exe of the same installation when that file exists. With no hit it runs the bare name conda.

When run finds no conda, it stops at its first step with Requirement 'conda' not found in PATH. There are two ways to fix this:

  • Open the Miniforge Prompt or the Anaconda Prompt from the Start menu and run the commands there. Or run conda init powershell once in that prompt, and open a new PowerShell window.

  • As a fallback, set CONDA_EXE to the full path of conda.exe in the window, before run:

    $env:CONDA_EXE = '<conda folder>\Scripts\conda.exe'

CONDA_EXE is all that run needs from conda, because every conda call of run uses that file. Without conda activate, call the environment's Python by its full path, <environment folder>\python.exe -m ostram run ..., as every stage runs under the Python that called the command. conda env list shows the environment folder.

Verify the installation

python -m ostram --help
python -m ostram inspect-resources
python -m ostram run --skip-pull --compile-only --scenarios A_Calibrated_BAU

The solver-free checks are listed under Tests in CONTRIBUTING.md. The last command above prepares the base model, builds A_Calibrated_BAU, compiles its inputs and stops after the solver datafile. It runs no solver.

From outside the checkout, name the project root explicitly:

python -m ostram --project-root <path to the clone> inspect-resources

Use --workspace or OSTRAM_WORKSPACE to place mutable state elsewhere. Explicit command-line values override environment variables. Inspection is read-only and does not create the workspace. The support BAU command is on the pipeline page.

Solvers

environment.yaml installs GLPK and CBC. CPLEX and Gurobi require their vendor installations and licences. Select the solver in config/execution/Config_MOMF_T1_AB.yaml. The tracked south_asia setup selects CPLEX, and the training setup selects CBC. For CPLEX, add the folder that holds cplex.exe to PATH in the session.

Verify a solver before a production run:

glpsol --version
cbc -stop
cplex -c quit

Use the compile-only route when validating without a solver:

python -m ostram run --skip-pull --compile-only --scenarios A_Calibrated_BAU

DVC

DVC is a package dependency and dvc.yaml uses only canonical package commands and workspace paths. Without --skip-pull, the OSTRAM runner initializes local DVC metadata when needed and pulls only when a remote is configured. With --skip-pull, it performs neither DVC initialization nor a pull. It does not use caller CWD to locate project data.

dvc remote list
python -m ostram run --skip-pull --compile-only --scenarios A_Calibrated_BAU

Generated DVC cache/tmp state and the central workspace are ignored. Maintained inputs, configuration, model files, and package resources remain tracked and must not be replaced with generated copies.

Quickstart

1. Install the editable package

Follow the installation page, then check from the project root:

python -m ostram inspect-resources

The last command reads representative input, configuration, model, and package resources without creating a workspace.

2. Choose project and workspace paths

An editable checkout is discovered automatically. For an installed package or an external working directory, provide the project bundle explicitly:

python -m ostram `
  --project-root <path to the clone> `
  --workspace "<path to a workspace>" `
  inspect-resources

The equivalent environment variables are OSTRAM_PROJECT_ROOT and OSTRAM_WORKSPACE. Command-line values take precedence. All resolved paths are absolute, and the caller's current directory is never searched for resources.

Supported Windows locations

Use a local, nonsynchronised location for both the project and workspace. Unicode and spaces are supported. Before a run, the final-output preflight must predict every final path at no more than 240 UTF-16 code units.

Deeply nested roots, network-mounted roots, and cloud-synchronised roots, including OneDrive, are unsupported. If the preflight fails, choose a shorter local root. The application must not silently truncate final output names.

3. Run a solver-free preparation gate

python -m ostram run --skip-pull --compile-only --scenarios A_Calibrated_BAU

--compile-only reaches the final preprocessed text inputs and stops before matrix creation, every solver adapter, cleanup, and result post-processing.

The run takes minutes. In one run on one machine, compiling two derived scenarios took about 20 minutes: A1 4 minutes, A2 45 seconds, A3 8 minutes, B1 5.5 minutes and B2 25 seconds. A3 and B1 are the longest stages. Other machines differ. Progress goes to stderr. When output is redirected in Windows PowerShell 5.1, the normal progress lines appear as NativeCommandError. The exit code decides success: $LASTEXITCODE is 0 after a successful run, which ends with OSTRAM compile-only run completed successfully.

Useful focused commands are:

python -m ostram transform --scenario A_Calibrated_BAU
python -m ostram compile-inputs --scenarios "A_Calibrated_BAU,B_Optimised_VRE"

4. Run the configured workflow

After selecting and configuring a solver in config/execution/Config_MOMF_T1_AB.yaml:

python -m ostram run --skip-pull --scenarios A_Calibrated_BAU

The runner conditionally prepares A1/A2 snapshots, materializes the exact registry selection, compiles it, and executes B2. Use --scenarios for an explicit comma-separated selection and the documented --skip-* flags when a stage is already satisfied.

For all 17 decision cases, use the portfolio sequence: solve A, then materialize and solve the remaining decision cases using that new A result. Support BAU has a separate standalone execution command and permits existing transmission plus committed additions. It is not the A scenario. The unfiltered default also includes C, which cannot be materialized before its A result exists.

The interactive display is compact and updates in place on stderr. Redirected output uses append-only status lines. Add --verbose to disable the moving display and stream complete child output. The detailed UTF-8 log is always at <workspace>/logs/<run-id>/run.log for an actual run.

5. Know where files belong

  • Maintained scenario workbooks: inputs/scenarios/
  • OSeMOSYS CSV authorities: inputs/osemosys_global/
  • Scenario policy: config/scenarios/
  • Compilation/execution configuration: config/compilation/ and config/execution/
  • Read-only package resources: ostram/resources/
  • Generated workbooks, compiled parameters, executables, and results: <workspace>/preparation, <workspace>/scenarios, <workspace>/compilation, and <workspace>/execution

workspace/ is ignored and created lazily. Do not copy maintained sources into it or treat generated state as source authority.

6. Run solver-free validation

The solver-free checks are listed under Tests in CONTRIBUTING.md. They call no matrix builder or solver.

OSTRAM and RDM: user guide

This guide takes you from a fresh clone to a finished RDM run. It is written for someone who runs the model, and who also wants to know which script runs when, what it reads and what it writes.

This guide is also a single HTML page, docs/html/OSTRAM_RDM_User_Guide.html, and every page of the documentation is in docs/html/OSTRAM_Complete_Documentation.html. Both are rebuilt from the Markdown pages with python tools/build_html_docs.py --bake.

It has four parts:

  1. The repository: what each folder holds and which stage of the pipeline uses it.
  2. The pipeline: what each command calls, stage by stage.
  3. The baseline: set up the training model and build, solve and check the root scenarios. This is what the training exercises do, and it comes first, because every RDM future starts from a root.
  4. RDM: describe futures in one Excel workbook, run them all, and collect the RDM CSVs.

The examples use the two-region training model (unescap_training: Bangladesh and India East), which solves in minutes. Part 5 says what changes for the South Asia model. The RDM futures page is the short reference for the RDM workbook and commands.

Every command runs from your OSTRAM folder, the root of the clone, in an Anaconda Prompt, with the environment active (step 3.1).

1.5 Folder names do not match the stage labels

The workspace folder names come from the original model-building scripts and predate the stage labels A1 to B2. Read them by what they hold, not by their prefix:

  • preparation\A1_Outputs\ is not only A1's output. It holds the A1 + A2 snapshots, every scenario and future that A3 builds, and the completed workbooks that B1 adds to each scenario's folder.
  • compilation\A2_Output_Params\ is B1's output, not A2's.
  • execution\A2_Outputs_Params_otoole\ is B2's output, not A2's.

The chain, as folders:

Stage Reads Writes
A1 + A2 inputs\osemosys_global\ (the raw OSeMOSYS Global CSVs) preparation\A1_Outputs\_post_a2_snapshot_<root>\ (built once, reused by later runs)
A3 the snapshot, and for futures the run folder's scenario.yaml preparation\A1_Outputs\A1_Outputs_<scenario>\: the A-O workbooks and, for derived scenarios and futures, the edit log apply_patches_CHANGES_<time>.json inside that folder

Part 5. The South Asia model

The same parts, with these differences:

  • Leave out --setup unescap_training: South Asia is the default. Its files are directly under workspace\ (for example workspace\rdm\<Run_Name>\), its inputs and configuration are the top-level inputs\ and config\, and step 3.3 is not needed.
  • The baseline is the root scenarios plus the 17 decision scenarios; the pipeline page gives the order (solve A_Calibrated_BAU first, then the rest with --a-result-seed).
  • Apply_VRE_Ceilings = Auto applies the shared solar and wind ceilings to every future, so F00 differs from the root by those ceilings.
  • The base-year pin keeps the reviewed 2023–2026 values of the calibrated technologies, even after a Set without years.
  • B2 solves with CPLEX by default; the model is larger, so run --compile-only first.
  • A future built on C_Target_VRE needs a solved A_Calibrated_BAU, passed with --a-result-seed <folder>.

Reference

What a future cannot do

  • Start from another derived scenario: a future starts from a root. Copy that scenario's changes into the future's rows.
  • Change the model's structure (a new country, technology or interconnector): that goes into the baseline (step 3.7).
  • Hold a gross import cap or an interconnector direction overlay.
  • Change CapacityFactor: an edit changes the first row of a technology and parameter, and that parameter has one row per timeslice.

Set, no years op: set_flat, value (every year, base years included)

Multiply_Ramp, years a to b, final factor f for each year y after a up to b: multiply by 1 + (f − 1)(y − a)/(b − a); then multiply by f for the years after b

Support BAU

The south_asia setup rule is: BAU permits existing transmission plus already committed additions, with no discretionary expansion beyond those commitments. Existing TotalAnnualMinCapacityInvestment values for the 18 interconnector TRN technologies are interpreted as the commitments. Their year is their commissioning year. No investment minimum is removed or changed.

For technology t and model year y, the final ceiling is:

TotalAnnualMaxCapacity[t,y] = ResidualCapacity[t,y]
  + sum(TotalAnnualMinCapacityInvestment[t,v]
        for model years v where 0 <= y-v < OperationalLife[t])

This uses the model's vintage survival rule: a committed addition is unavailable before commissioning and expires at the operational-life boundary. Residual capacity keeps its existing year-by-year trajectory. With the unchanged annual investment minima, the ceiling prevents discretionary additions. The final ceiling rows use Projection.Mode = User defined: B1 deliberately omits rows marked EMPTY, even when their year cells contain numbers.

The policy runs only on the final south_asia BAU output, after disposable restriction-state export and delivery. Shared preparation, post-A2 snapshots, and inherited Restrictions retain their existing values. The training setup does not enable this policy. Validation remains enabled and does not apply repairs. support_bau_transmission.json beside the final parametrization workbook records all 504 technology/year ceilings and sources.

Capital annualization

ostram.pipeline.execution.annualization is reached by B2 when annualize_capital: true in config/execution/Config_MOMF_T1_AB.yaml. It converts the lump-sum CapitalInvestment and CapitalInvestmentStorage results into Capital Recovery Factor (CRF) payment streams and appends them to the combined inputs/outputs CSV as new rows in two new columns, CapitalInvestmentAnnualized and CapitalInvestmentStorageAnnualized. The new rows carry Future, Scenario, REGION, TECHNOLOGY (or STORAGE) and YEAR, with every other set column blank, exactly like the CapitalInvestment rows they derive from.

The lifetime and discount rate are the ones the model solved with: OperationalLife / OperationalLifeStorage from the input parameters in the combined file (falling back to the datafile param default), and DiscountRate / DiscountRateStorage from each scenario's compiled datafile Executables/<Scenario>_<Future>/<Scenario>_<Future>.txt. A non-integer lifetime is rounded half-up to a whole number of payments. There are no built-in numeric defaults: a missing datafile, lifetime or rate stops the step with an error naming what is missing.

The combined file is read in chunks and rewritten as a stream, so the step never loads the whole campaign table. Running it twice on the same file is refused. It can also be run on an existing combined file:

python -m ostram.pipeline.execution.annualization --input workspace\execution\OSTRAM_StorageDelay_Combined_Inputs_Outputs.csv --executables workspace\execution\Executables

--discount-rate and --asset-lifetime override the model values for every series when an explicit sensitivity is wanted.

The order is load-bearing in these places.

  • The retirement rule runs before the build-cap rule, because the build-cap rule reads the ResidualCapacity that retirement writes.
  • The build-cap rule skips interconnectors. The relaxation rule sets their caps afterwards from their residual capacity, and the direction overlay runs after the relaxation rule.

  • The storage minimum investment rule writes TotalAnnualMinCapacityInvestment for the storage families, which the build-cap rule exempts. The reason for its position is not recorded.
  • The internal transmission rule runs after the stage 1 template merge, because that merge rewrites OperationalLife, and the rule has to win.
  • The base-year pin runs last, so that reviewed values are the final values. A derived scenario applies it again after its edits, so that the shared ceilings and the edits cannot replace a reviewed value.

Build caps

The build-cap rule sets each cap in five steps, in a fixed order. The settings are in config/scenarios/<root>/build_cap_rule.yaml.

  1. Formula. The required growth of a country-region in a year is the increase of its demand-scaled fleet from the year before. It is zero when the fleet shrinks. Each technology's cap starts as the required growth multiplied by the technology's share of the 2024 fleet and by the margin factor.
  2. Cap multiplier. The cap is multiplied by the factor for the year. Years between the listed years are interpolated.
  3. Family limits. A family takes the cap multiplier only up to its family limit. A family limit of 1.0 or less locks the family at its 2024 share. Families absent from the list take the full cap multiplier.
  4. Technology top-up. Any cap of an unlocked family that is below the top-up value is raised to that value.
  5. Adequacy top-up. When the caps of a country-region add up to less than the adequacy share multiplied by the demand-scaled fleet, every cap is multiplied by the same factor so that the sum reaches that amount. The adequacy share is interpolated between the listed years.

If a cap would be at or below the minimum investment of the same year, the rule sets it to 1.01 times that minimum. The storage families are exempt: both of their caps are set to 9999. Interconnectors are skipped.

In A the cap multiplier stays at 1.0, so the family limits there only decide which families are locked, and the technology top-up of 0.0 GW raises nothing. In B and C, solar and wind have no family limit and take the full cap multiplier.

The reason for the top-ups

The rule sets the caps before the model runs, so it can only use the fleet that is in the input data. The formula ties each cap to the growth of the demand-scaled fleet, and that fleet counts only plants that already exist. As those plants retire, the fleet grows more slowly, and late in the horizon the formula allows very little new building even though demand still rises. With too little room, the model turns to the backstop. The technology top-up and the adequacy top-up give back the room lost as plants retire. The adequacy share is 0.0 until 2040, so the calibrated years keep their caps. The caps set the most that may be built. The model still chooses what it builds at least cost.

Other ways to set build caps

These are alternatives for discussion. None of them is part of OSTRAM.

Caps set by hand. A modeller enters one cap for every technology, country-region and year from plans and expert judgement. The values are transparent, and each one must be revised when demand, retirements or committed additions change.

A growth-rate limit inside the model. A constraint lets each year's new capacity grow by at most a set fraction of the capacity that the model itself has built or kept in the year before. The model then sees its own fleet, and the limit becomes part of the optimisation.

Solving repeatedly while updating the fleet. The model is solved, the caps are recomputed from the solved fleet, and the model is solved again until the caps stop changing. Each round is a full solve.

Data-based build rates. Caps come from observed construction rates, for example the largest annual addition of a technology in a comparable system, scaled to the size of the fleet. They need a dataset of historical additions for every technology family.

Gas and oil allowance

Gas and oil plants that would otherwise be blocked may still add up to 0.5 GW per year in each country-region. This lets each one meet its reserve margin with real plants instead of the emergency backstop. The value is a modelling choice. You can change it to explore its effect.

The same value also replaces a build cap of 9999 for these technologies.

The value is in inputs/execution/firm_capacity_fallbacks_by_cr.xlsx, sheet fallbacks, column TotalAnnualMaxCapacityInvestment, one row per country-region. Column TotalAnnualMaxCapacity of the same sheet holds the 10 GW fallback for a total capacity cap of 0. The settings that switch the step on and select the technologies and the replaced values are in config/execution/Config_MOMF_T1_AB.yaml: reserve_margin_xlsx_active, reserve_margin_xlsx_target_prefixes and reserve_margin_xlsx_sentinel_values.

Storage delay

No new storage can be built before 2028. This reflects the years needed to plan and build storage; existing storage is kept. The five-year delay is a modelling choice, the same in every scenario. You can change it to explore its effect.

The settings are in config/execution/Config_MOMF_T1_AB.yaml: storage_delay_active switches the step on, storage_delay_first_n_years sets the number of blocked years from the first model year, and storage_delay_storage_prefixes selects the storage families. The output file names keep the suffix StorageDelayN5 whatever number of years is set, because the suffix is the separate setting storage_delay_suffix.

Scenario edits

A derived scenario is built from its parent's A-O workbooks by ostram/pipeline/scenarios/scenario_edits.py, which reads the scenario's file config/scenarios/<name>/scenario.yaml. Terms are in the glossary.

Order of the build

  1. The parent's folder A1_Outputs_<parent> is copied to A1_Outputs_<scenario> under workspace/preparation/A1_Outputs/. An existing target folder is first copied to A1_Outputs_<scenario>_PREPATCH_<stamp>, unless backups are skipped. The run command skips them.
  2. The shared VRE ceilings are applied, unless the scenario file sets apply_vre_ceiling_layer: false.
  3. The edits in the file's edits list are applied in list order. Each edit sees the changes of the earlier ones. When the file names another scenario in reuse_edits_from, that scenario's edits are applied first.
  4. A-O_Parametrization.xlsx is saved and the base-year pin is applied again.
  5. The edit log is written to the target folder.

For B_Opt_DirBidir and B_Opt_DirContractual the overlay is applied after these steps.

Demand edits

An edit whose sheet is Demand_Projection changes the scenario's A-O_Demand.xlsx instead of A-O_Parametrization.xlsx. That sheet has one SpecifiedAnnualDemand row per demand fuel, keyed by its Fuel/Tech column, so a demand edit names its rows with exactly one of fuel, fuels and fuel_prefix and needs no param (when given, it must be SpecifiedAnnualDemand). It holds values, op: multiply (with optional years) or op: set_flat:

- sheet: Demand_Projection
  fuel_prefix: ELC
  op: multiply
  factor: 1.15
  years: [2030, 2031, 2032]

Reusing another scenario's edits

A scenario file can name another derived scenario whose edits it applies before its own:

scenario: B_Opt_IndiaCostsFuel
base_scenario: B_Optimised_VRE
reuse_edits_from: B_Opt_IndiaCosts
edits:
- sheet: VariableCost
  techs: [MINCOABGD, MINCOABTN, MINCOALKA, MINCOAMDV, MINCOANPL]
  param: VariableCost
  op: copy_from_tech
  source_tech: MINCOAIND

The named scenario must have its own file under config/scenarios/, the same base_scenario, and no reuse_edits_from of its own. Otherwise the build stops before it copies the parent, with a message that says which rule failed. The named scenario's shared VRE ceilings setting is not used; the reusing scenario's own setting applies.

The shared VRE ceilings

Before the edits, for each of the 20 technologies in vre_ceilings, the build sets TotalAnnualMaxCapacity to the ceiling in every year, lowers TotalAnnualMaxCapacityInvestment and TotalAnnualMinCapacityInvestment to the ceiling where they are higher, and, where the ceiling lowered the previous maximum, scales a positive activity lower limit by the same ratio. The ceiling is written as a flat value. A ceiling above the previous maximum raises it; the pipeline never takes the lower of the two.

Gross import cap

A scenario file can hold a gross_import_cap block. It is a policy, not an edit. ostram/pipeline/execution/gross_import_cap.py reads it when B2 converts the compiled files into the solver datafile. The edit stage and the edit log do not see it. B_Opt_Clipped_GrossImportCap15 holds one for six countries. A block for one country reads:

gross_import_cap:
  countries: [BGD]
  fraction: 0.15
  first_year: 2027
  last_year: 2050
Field Meaning
countries A list of country codes: BGD, BTN, IND, LKA, MDV and NPL. A repeated code or a code outside the list stops the run. India is one country, with its five regions.
fraction The cap as a share of the country's annual demand, from 0 to 1. A value outside that range stops the run.
first_year, last_year The first and the last year of the cap, both included. first_year must not be later than last_year.

In each of these years, the gross electricity that the country receives from other countries must not exceed fraction times its annual demand. The received electricity is the sum, over the timeslices, of the activity of each flow multiplied by the year split and by the output activity ratio. The annual demand is the SpecifiedAnnualDemand of the country's demand fuels, the fuels that start with ELC, the country code and end with 03. For India that is the sum of its five regions.

The flows that count are the modes of the cross-border TRN technologies whose two country codes differ and whose output fuel starts with ELC and the code of the country, with a positive output activity ratio in the compiled OutputActivityRatio.csv. Links between Indian regions are excluded, because both ends are in India. A flow from India into another country counts for that country.

The cap is applied at compilation. The final datafile holds it as set D4ImportCountry, set D4ImportDemand, set D4ImportFlow and param D4ImportFraction, in workspace/execution/Executables/<scenario>_0/Pre_processed_<scenario>_0_StorageDelayN5_OpenBCK_RMCarefulXLSX.txt. A scenario without the block has an empty set D4ImportCountry. The edit log does not list the cap. The run stops with an error when a scenario holds the block and the model file lacks the parameter D4HistoricalTradeActive.

The edit log and the backup folder

The edit log is apply_patches_CHANGES_<stamp>.json in A1_Outputs_<scenario>. It records the scenario, its parent, the time stamp, the backup folder, every changed cell with its old and new value, every row created, every tech_prefix member skipped for lack of a row, the number of ceilings applied, the record of the base-year pin and, for a scenario with reuse_edits_from, the reused scenario and its number of edits. The backup folder, when one is made, is A1_Outputs_<scenario>_PREPATCH_<stamp> beside the target.

The cells list also holds the cells of the shared VRE ceilings, so it is longer than the edits of the file suggest. This command shows the cells of one parameter:

(Get-Content apply_patches_CHANGES_<stamp>.json -Raw | ConvertFrom-Json).cells |
  Where-Object { $_.param -eq 'CapitalCost' } | Format-Table tech, year, old, new

The old value of a cell is its value when the edit ran. That is the parent's value, unless the shared VRE ceilings or an earlier edit of the same file changed the cell first. A comparison with the parent therefore needs no build of the parent scenario.

Edits that match nothing

The build stops with an error when an edit changes nothing:

  • a tech or techs edit finds no row for the parameter and create_if_absent is false;
  • a create_if_absent edit names a technology that is absent from the workbook, or a parameter that is absent from every sheet;
  • a tech_prefix edit matches no technology;
  • a values edit, or a multiply edit with years, names a year that is not a year column; the message lists the missing years;
  • a shared VRE ceiling finds no TotalAnnualMaxCapacity row for its technology;
  • a copy_from_tech edit finds no row of its source_tech for the parameter.

The message names the scenario, the edit and the reason, and suggests the closest name when one exists:

Scenario B_Opt_MyTest: the edit to TotalAnnualMaxCapacity for "PWRSOLBGXX" changed nothing. No technology has that name. Did you mean PWRSOLBGDXX?

The other reasons read Sheet "<sheet>" has no parameter "<param>"., No technology starts with "<prefix>"., None of the years <years> is a column in the workbook. and Sheet "<sheet>" has no <param> row for it. A missing copy_from_tech source reads has no source row. Sheet "<sheet>" has no <param> row for <source_tech>. The run command prints the message and exits with code 1.

RDM futures

Robust Decision Making (RDM) asks how a plan performs across many futures. In OSTRAM a future is a derived scenario: a root scenario plus an ordered list of edits. The rdm command builds those derived scenarios from one Excel workbook, runs them all through the normal pipeline, and collects one input CSV and one output CSV for the whole set.

You work only in the workbook. Nothing under config/ or inputs/ changes: each run lives in its own folder, <workspace>/rdm/<Run_Name>/.

First time? Follow the OSTRAM and RDM user guide: it goes from a fresh clone through the baseline to the RDM results, and explains which script runs at each step. This page is the short reference.

Quick start

# 1. A workbook with dropdowns filled from the prepared root
python -m ostram --setup unescap_training rdm template --out Interface_OSTRAM_RDM.xlsx

# 2. Fill the Futures, Future_Changes and Uncertainty_Table sheets, then
python -m ostram --setup unescap_training rdm run --interface Interface_OSTRAM_RDM.xlsx

--setup and --workspace go before rdm, as for every command; without them the South Asia setup is used. The root must be prepared once (any run of it, --compile-only is enough) before template can fill the technology and fuel dropdowns; the template works without them, with empty dropdowns.

Command What it does
rdm template --out <file> [--root <root>] [--blank] Writes the interface workbook. --blank leaves out the worked example.
rdm generate --interface <file> [--overwrite] Checks the workbook and writes the run folder. Runs nothing. Use it to review the futures before a long run.
rdm run --interface <file> [--overwrite] [--compile-only] [--a-result-seed <dir>] [--env-name <env>] generate, then A3, B1 and B2 for every future, then collect.
rdm collect --run <Run_Name or folder> Gathers the CSVs again from the solved futures, for example after a run stopped part way.

run refuses an existing run folder unless --overwrite is given; change Run_Name to keep earlier runs.

How a future is built

  1. Copy the root named in Setup > Base_Scenario.
  2. Apply the shared VRE ceilings, when they apply (Apply_VRE_Ceilings; Auto uses them when the setup defines them, which South Asia does and the training setup does not).
  3. Apply the future's rows of Future_Changes, top to bottom.
  4. With Samples_Per_Future above 0, apply one sampled value of every uncertainty in Uncertainty_Table whose Applies_To includes the future.
  5. Re-apply the base-year pin, as for every derived scenario.

Steps 1, 2, 3 and 5 are the existing scenario edits; the rdm command only writes the edits for you.

Layered sampling

With Samples_Per_Future = N, each named future F01 that has at least one uncertainty becomes F01_s001 to F01_sN. With Run_Central_Future = Y, F01 itself, without sampled uncertainties, runs as well. A future that no uncertainty applies to runs once, under its own name.

The values are drawn by Latin Hypercube sampling, uniform between Min and Max, from Random_Seed. Sample s uses the same draw in every future, so F01_s007 and F02_s007 differ only by the futures' own changes. Two rows linked with Linked_To take the same position in their ranges.

The sampled uncertainties apply after the future's changes, so a Multiply uncertainty scales the future's path, not the root's. For example, a future that raises demand by 15 per cent and a demand uncertainty of 0.9 to 1.1 give demand between 103.5 and 126.5 per cent of the root.

RDM_Outputs.csv The exported result variables of every future, in the same layout.
RDM_Run_Status.csv For each future: solved, compiled (inputs only, as after --compile-only) or missing, with the paths of its B2 files.

RDM_Inputs.csv and RDM_Outputs.csv join to RDM_Experiment_Design.csv on Future_ID. They are the record of the run: the per-future folders under <workspace>/execution/Executables/ and <workspace>/preparation/A1_Outputs/ are reused by the next run with the same Future_IDs. rdm run deletes each future's Executables/<future>_0 folder before it starts, so a future that fails or is only compiled never shows an earlier run's results.

The OSTRAM and RDM user guide walks through a run from a fresh clone, explaining what happens inside at each step.

How the futures reach the pipeline

rdm run sets the environment variable OSTRAM_RDM_FUTURES to the run's futures.yaml and calls python -m ostram run --skip-pull --scenarios <futures>. While it is set, the scenario registry adds each listed future as a derived scenario of its root, with its scenario.yaml in the run folder, so A3, B1 and B2 treat the futures exactly like the scenarios of config/scenarios/. Outside an rdm run the variable is unset and the registry is unchanged.

B2 solves the futures one after another unless parallel: True is set in the execution configuration (see configuration). A future uses its root's entries in cbc_primal_tolerance_by_scenario and cplex_numerical_emphasis_scenarios, since it has the root's numerics. With CBC, a future is solved with primal simplex (-primalS): CBC's default dual simplex can cycle for hours on these storage models, and futures cannot be tuned one by one. rdm_cbc_simplex: dual in the execution configuration restores the default. A future that fails is recorded and the next one still runs; the run then ends with an error that names the failed futures, and they show as compiled in RDM_Run_Status.csv. Outside an RDM run, B2 still stops at the first failure.

Limits

  • A future's root is one of the setup's roots. A future cannot build on another derived scenario; copy that scenario's changes into the future's rows instead.
  • A future has no gross_import_cap and no interconnector direction overlay.
  • The edits change the first row of a technology and parameter on a sheet, so CapacityFactor (one row per timeslice on Capacities) is not a target.
  • A future built on C_Target_VRE needs a solved A_Calibrated_BAU, passed with --a-result-seed, as for C_Target_VRE itself.

Naming Conventions

Technology Codes

Technology names in OSTRAM follow a structured format that encodes the technology type, energy source, country, and region:

{PREFIX}{SOURCE}{COUNTRY}{REGION}

Code Meaning

Cross-Border Interconnector Codes

The literal cross-border transmission line between two countries/regions uses a different, longer pattern than the per-country technologies above:

TRN{ORIGIN 5-char}{DEST 5-char}

Each 5-char block is a 3-letter country code + 2-letter region code (13 characters total after TRN). Examples from the live data: TRNBGDXXINDEA (Bangladesh ↔ India-East), TRNINDEAINDNE (India-East ↔ India-North-East). These pre-exist in the raw input data and have their fuel codes rewritten by Stage A2; TRNNLI*-prefixed per-country technologies (not to be confused with this pair-level TRN code) represent unplanned candidate lines rather than existing/committed ones.

The interconnector technologies

The South Asia model has 18 technologies of this form. Eleven link two countries. Seven link two regions of India and are domestic. The first block of the name is the first end and the second block is the second end. The blocks are not in alphabetical order, as TRNBTNXXBGDXX and TRNMDVXXINDSO show. One technology serves both directions: its mode 1 sends electricity from the first end to the second and its mode 2 sends it the other way.

Conversion Matrices

Three matrices map timeslices to temporal dimensions, defined directly in Config_MOMF_T1_A.yaml:

Model Architecture

OSTRAM uses a single-region (GLOBAL) architecture where geographic granularity is embedded in the technology and fuel naming conventions. Each country/region's technologies operate independently, connected only through explicit cross-border interconnector (TRN) technologies.

Energy Flow

  1. Mining technologies (MIN) extract primary commodities (coal, gas, oil, etc.), country-level (not region-split).
  2. Power technologies (PWR) convert fuels into electricity: ELC*00 for renewable output, ELC*01 for non-renewable output.
  3. Renewable resource technologies (RNW) supply renewable primary energy, region-split.
  4. Grid-tier conversion technologies (RNWTRN/PWRTRN/RNWRPO/TRNRPO/RNWNLI/TRNNLI, one set per country-region, added by Stage A2) convert ELC*00/ELC*01 into ELC*02, the tier available to meet domestic demand.
  5. Dispatch technology (DSPTRN) routes electricity to/from cross-border interconnections: Mode 1 converts ELC*02 → ELC*03 (dispatch-ready for export); Mode 2 converts ELC*04 (imported) → ELC*03 (dispatch-ready again, for local use).
  6. Cross-border interconnector technologies (TRN{origin}{dest}, a pre-existing pair-level code, distinct from the per-country A2-generated technologies above) transport electricity between countries/regions, consuming ELC*03 at the origin and producing ELC*04 at the destination.
  7. Storage technologies (LDS/SDS) balance supply and demand across timeslices, exchanging with the ELC*00 renewable-output tier.

Facts that apply across scenarios

  • Every registered derived scenario applies the shared VRE ceilings, including the scenarios without "Clipped" in their name. B_Opt_TxCap150 is therefore B_Opt_Clipped plus the transmission cap, and the scenario to compare it with is B_Opt_Clipped.
  • The ceilings set flat values. The pipeline never takes the lower of the previous value and the ceiling; a ceiling above the previous value raises it. The scenario edits page describes the step.
  • B_Opt_TradeCap15 and B_Opt_Clipped_GrossImportCap15 are different limits. B_Opt_TradeCap15 sets fixed activity upper limits on four Bangladesh import corridors and zero activity on Bangladesh's new and repowered internal lines from 2027, through scenario edits. B_Opt_Clipped_GrossImportCap15 caps the gross received imports of each of the six countries at 15 per cent of its annual demand in 2027 to 2050, through a constraint that B2 builds from the compiled demand and output ratios.
  • C_Target_VRE_Clipped restates the Maldives solar assumption for 2028 that C_Target_VRE already carries from the scenario workbook.

The applied values and the historical limits

Each ceiling in south_asia.yaml was chosen once as the lower of the atlas-based figure and the historical B_Optimised_VRE limit. Four values therefore hold the historical limit in place of the atlas figure: BTN solar 1.8102 GW (atlas figure 5), INDEA wind 0 (atlas figure 8), INDNE wind 0 (atlas figure 0.5) and NPL wind 0 (atlas figure 2). The three clips below are the cases where the atlas figure itself binds.

The pipeline applies every ceiling as a fixed value in all years of a derived scenario. It never computes the lower of the previous workbook value and the ceiling, and a ceiling above the previous value raises it. The annual investment bounds of the same technology are lowered to the ceiling where they exceed it. The scenario edits page describes the step.

The three clips

  • LKA solar 16 ★ — well supported, but it matches a 2050 scenario build (ADB/UNDP), not pure technical potential (ADB technical ≈ 6 GW).
  • BGD onshore wind 3 ★ — cite-gap. Only literature figure is NREL/SREDA ">30 GW gross" (self-flagged unrealistic).
  • MDV onshore wind 0 ★ — defensible but not literally zero. Roadmap + Rinaldi et al. (2019): onshore wind "excluded from the energy strategy", only ~80 MW niche (Greater Malé).

The current demand accounting

The demand of Bangladesh, Bhutan, the five India regions, Nepal and Sri Lanka for 2023 to 2050 is an upstream requirement. The demand balance of the model credits the actual internal transfer losses once, while the physical input and output ratios of the internal transmission families stay as they are. Border losses receive no such credit, and the Maldives is excluded. The 3% above is the physical loss of the internal transmission families, and this accounting does not remove it. The sources are the demand balance in model/osemosys_fast_preprocessed.txt and the row "Trade and upstream-demand accounting" of the README sheet in inputs/scenarios/OSTRAM_Scenario_Inputs.xlsx.

Convention: corridor code TRN<SRC><DST>; forward = SRC→DST, reverse = DST→SRC, bidirectional = both modes active (omit from config).

Each corridor's direction is set to its real-world governing flow, established from primary sources (PPAs, commissioned assets, official plans).
