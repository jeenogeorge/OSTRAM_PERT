OSTRAM and RDM: user guide

This guide takes you from a fresh clone to a finished RDM run. It is written for someone who runs the model, and who also wants to know which script runs when, what it reads and what it writes.

This guide is also a single HTML page, docs/html/OSTRAM_RDM_User_Guide.html, and every page of the documentation is in docs/html/OSTRAM_Complete_Documentation.html. Both are rebuilt from the Markdown pages with python tools/build_html_docs.py --bake.

It has four parts:

  1. The repository: what each folder holds and which stage of the pipeline uses it.
  2. The pipeline: what each command calls, stage by stage.
  3. The baseline: set up the training model and build, solve and check the root scenarios. This is what the training exercises do, and it comes first, because every RDM future starts from a root.
  4. RDM: describe futures in one Excel workbook, run them all, and collect the RDM CSVs.

The examples use the two-region training model (unescap_training: Bangladesh and India East), which solves in minutes. Part 5 says what changes for the South Asia model. The RDM futures page is the short reference for the RDM workbook and commands.

Every command runs from your OSTRAM folder, the root of the clone, in an Anaconda Prompt, with the environment active (step 3.1).

Part 1. The repository

1.1 Top-level folders

Your clone (for example the folder OSTRAM_PERT) holds the source: code, inputs and configuration. Everything the pipeline generates goes into workspace\, which Git ignores.

Part 2. The pipeline

2.1 Commands and what they call

You type It calls Does
python -m ostram example prepare unescap_training ostram.examples → setup_workspace.prepare_setup Creates the training workspace and copies its inputs into authorities\.
python -m ostram [--setup S] run --scenarios … ostram.pipeline.orchestration The whole pipeline, A1 to B2 (2.2).
… run … --compile-only the same A1 to B2, stopping before the LP and the solver.
python -m ostram [--setup S] transform --scenario R ostram.pipeline.scenarios.transform A3 for one root only.
python -m ostram [--setup S] compile-inputs --scenarios … ostram.pipeline.compilation.runner B1 only.
python -m ostram example report unescap_training [--capture L] ostram.examples → ostram.reporting.training_dashboard The dashboard; --capture saves the latest results as snapshot L.
python -m ostram --setup S country template / merge / validate ostram.pipeline.preparation.country_commands Add a country's data (exercise A).
python -m ostram --setup S rdm template / generate / run / collect ostram.rdm.cli RDM (Part 4). rdm run calls orchestration itself.

2.2 The stages of run

run checks the conda environment, skips DVC with --skip-pull, then runs five stages. Each stage is a separate Python process, started as python -B -m <module>; the full command lines are in the run log.

Stage Module Reads Writes (under the workspace) When it runs
A1 Prepare the base model ostram.pipeline.preparation.base_inputs the OSeMOSYS Global CSVs, Config_country_codes.yaml, Tech_Country_Matrix.xlsx, the workbook templates, Config_MOMF_T1_A.yaml preparation\og_csvs_inputs\, preparation\extra_inputs\, A1_Outputs_<root>\ for all four roots Only when a needed root has no post-A2 snapshot (the first run in a workspace).
A2 Add the transmission network ostram.pipeline.preparation.transmission Config_country_codes.yaml, the roots' workbooks the grid-tier and interconnector rows, then _post_a2_snapshot_<root>\ Together with A1.
A3 Build the scenarios ostram.pipeline.scenarios.materializer the registry, the scenario and timeslice workbooks, the roots' rule YAMLs, each derived scenario's or future's scenario.yaml A1_Outputs_<root>\, A1_Outputs_<scenario>\, _scenario_materialization.json Every run, for the selected scenarios and the roots they need.
B1 Compile ostram.pipeline.compilation.runner, which runs …compilation.compiler per scenario the scenario's four A-O workbooks, extra_inputs\, the compilation configuration compilation\A2_Output_Params\<scenario>\*.csv Every run.
B2 Run and collect ostram.pipeline.execution.runner → …execution.orchestrator the compiled CSVs, Config_MOMF_T1_AB.yaml, model\osemosys_fast_preprocessed.txt, firm_capacity_fallbacks_by_cr.xlsx execution\A2_Outputs_Params_otoole\<scenario>\, execution\Executables\<scenario>_0\, the combined CSVs Every run; --compile-only stops it after the datafile.

2.3 Inside A3

A root (for example B_Optimised_VRE) is rebuilt from its post-A2 snapshot in a working folder scenarios\_run_<time>\, through ostram.pipeline.scenarios.transform:

A3 step Scripts (in ostram\pipeline\scenarios\) What it does
Stage 0 transformations\scenario_workbooks Takes the root's rows of the scenario workbook, merged over the BAU rows.
Stage 1 transformations\merge_timeslices, extract_ao_extensions, ao_extension_decisions, update_ao_from_extensions, apply_manual_fixes, propagate_timeslice_fabric Writes the workbook's values and any new technologies into the A-O workbooks; applies the 20 timeslices.
Stage 1b insert_reserve_margin, add_max_capacity_investment_rule, fix_elc_pmode_revert, pre_solver_validation Reserve margin, investment caps, checks.
Stages 2–3 add_ao_c2a, fix_pwrpet_clear, fix_trn_residuals, clear_stale_unbinding_caps, cap_trn_to_residual Unit conversions; interconnector residual capacities and caps.
Stage 5, the root's rules rules\*.py, in the order of the Control sheet, each reading config\scenarios\<root>\<rule>.yaml For the training roots: BAU build cap; A_Calibrated_BAU retirement, build cap, minimum capacity floors, interconnectors; B_Optimised_VRE retirement, build cap, interconnectors, interconnector direction, storage minimum investment; C_Target_VRE retirement, build cap, VRE targets (from the solved A_Calibrated_BAU), interconnectors, storage minimum investment.
Shared rules rules\apply_interconnector_costs, apply_internal_transmission, apply_internal_tx_losses, then apply_base_year_pin where the setup uses it (South Asia, not training) Costs and losses of the grid; the reviewed 2023–2026 values.
Stage 6 transformations\sync_og_to_ts20, transform Writes the finished A-O workbooks to A1_Outputs_<root>\.

A derived scenario or an RDM future does not go through these stages: it starts from the root's finished A1_Outputs_<root>\. scenario_edits.py copies that folder to A1_Outputs_<scenario>\, applies the shared VRE ceilings when switched on, applies the scenario's edits in order, re-applies the base-year pin where the setup uses one, and writes the edit log.

2.4 Inside B2, for one scenario

B2 step Module Writes, in execution\Executables\<S>_0\
Normalise execution.runner (the CSVs in execution\A2_Outputs_Params_otoole\<S>\)
Convert to a datafile otoole <S>_0.txt, and <S>_0_Input.csv (the inputs as a table)
Preprocess execution.preprocess Pre_processed_<S>_0.txt
Storage delay model_file_adjustments.storage_delay …_StorageDelayN5.txt and an adjusted model file
Open backstop caps model_file_adjustments.open_pwrbck_caps …_OpenBCK.txt
Reserve-margin fallbacks model_file_adjustments.reserve_margin_repair_xlsx …_RMCarefulXLSX.txt: the datafile the solver sees
--compile-only stops here
LP glpsol --wlp …_output.lp
Solve CBC (training) or CPLEX (South Asia) …_output.sol; B2 accepts only an optimal solution
Results otoole and the concatenation Outputs\, …_output.csv (the results as a table)

After the last scenario of the run, B2 stacks every scenario folder in Executables\ into execution\OSTRAM_StorageDelay_*.csv.

Part 3. The baseline

This part follows the training exercises: set up the training model, then build and solve its root scenarios. Do it before RDM. Every RDM future starts from one of these roots, so they must build and solve on your machine first, and their results are the reference the futures are compared with.

Step 3.1. Open the prompt

cd <your OSTRAM folder>
conda activate OSTRAM-env
set PYTHONUTF8=1

In PowerShell the last line is $env:PYTHONUTF8 = '1'. Repeat this in every new prompt. Every stage runs under the Python of the active environment, and PYTHONUTF8=1 stops Windows from misreading the model files.

Step 3.2. Be on the RDM branch

The first time:

git fetch origin
git switch feat/rdm-futures

Later, to get new changes: git pull. Check with:

git branch
python -m ostram rdm --help

git branch puts * next to feat/rdm-futures, and the help lists template, generate, run and collect. If rdm is an unknown command, the environment runs OSTRAM from another folder: python -c "import ostram; print(ostram.__file__)" shows which; run pip install -e . from this clone.

Step 3.3. Prepare the training model (once)

python -m ostram example prepare unescap_training

Inside. ostram.examples creates workspace\setups\unescap_training\ and copies the training inputs into its authorities\ folder (1.4). The configuration is not copied: every stage reads it from examples\unescap_training\. When you edit an original input later, the next command refreshes its copy. No model is built yet. To start again from scratch, delete workspace\setups\unescap_training\ and run this step again.

Step 3.4. Build the roots without solving

python -m ostram --setup unescap_training run --scenarios "A_Calibrated_BAU,B_Optimised_VRE" --compile-only --skip-pull

Inside, in order (2.2):

  1. A1 + A2, the first time only: the base model is built from the OSeMOSYS Global CSVs for all four roots, the grid is added, and each root gets its snapshot in preparation\A1_Outputs\_post_a2_snapshot_<root>\.
  2. A3: BAU is built first, because A_Calibrated_BAU inherits its restrictions; then A_Calibrated_BAU and B_Optimised_VRE, each with the rule scripts of its Control-sheet row (2.3).
  3. B1: the two roots are compiled to CSVs.
  4. B2: the datafiles are written; no LP, no solve.

Check. preparation\A1_Outputs\A1_Outputs_B_Optimised_VRE\A-O_Parametrization.xlsx exists, and the console ends with OSTRAM compile-only run completed successfully.

Step 3.5. Solve the roots

python -m ostram --setup unescap_training run --scenarios "A_Calibrated_BAU,B_Optimised_VRE" --skip-pull

A1 and A2 are skipped (the snapshots exist); A3, B1 and B2 run again, and B2 now writes the LP and solves each root with CBC. Then:

python -m ostram --setup unescap_training run --scenarios "C_Target_VRE" --skip-pull

C_Target_VRE sets its renewable targets from the solved A_Calibrated_BAU, which the registry finds in execution\Executables\A_Calibrated_BAU_0\ of the same workspace. That is why A is solved first.

Check. Each root has an …_output.csv in its execution\Executables\<root>_0\ folder, and the log shows CBC solution status: Optimal.

Step 3.6. Capture the baseline and look at it

python -m ostram example report unescap_training --capture baseline
python -m ostram example report unescap_training

The first command copies the latest combined results (execution\OSTRAM_StorageDelay_Combined_Inputs_Outputs.csv) to reports\snapshots\baseline.csv, and both write the dashboard reports\unescap_training.html. Open it in a browser. Later snapshots (with another --capture label) can be compared with this baseline.

Step 3.7. Changing the model's structure (exercises A and B)

A new country or a new interconnector changes the structure of the model: new technologies, fuels and regions. That belongs in the baseline, not in RDM, because it reaches stages A1 and A2 and configuration files that every scenario shares. The training exercises do it like this:

Exercise What changes Where Picked up by
A: add a country The country's data, generated with country template, merged into the OSeMOSYS Global inputs with country merge, checked with country validate the workspace copy of the inputs A1
The country in country_data and countries config\preparation\Config_country_codes.yaml A1, A2
Its technologies and its firm-capacity row technology_types.csv, firm_capacity_fallbacks_by_cr.xlsx A3, B2
B: add an interconnector Rows in Interconnector_Params and Fixed_Horizon_Parameters the workspace copy of the scenario workbook A3, stage 1
The technology as an interconnector, and its extension decision technology_types.csv, ao_extension_decisions.csv A3
Its investment caps per root config\scenarios\<root>\relax_interconnectors.yaml A3, the root's rules

After such a change, rebuild the baseline from step 3.4; when A1 or A2 inputs changed, delete the workspace and start from step 3.3. The exercise pages use an older version's names (--profile unescap, examples\unescap\); with this code they are --setup unescap_training and examples\unescap_training\. The training setup also lists the exact technologies and fuels its compiled model may hold (domain_contract in setup.yaml), so new ones must be added there too.

Once the structure is in the baseline, RDM can vary it: for example, futures with and without the new interconnector, or with its cost and capacity sampled (Part 4).

Part 4. RDM futures

With the baseline in place, RDM runs the same model across many futures. A future is the root plus a list of changes. You describe the futures in one Excel workbook; rdm run builds each one as a derived scenario of the root (2.3), runs the normal pipeline on all of them, and collects one input CSV and one output CSV.

Step You type OSTRAM does
4.1 rdm template Writes the Excel interface
4.2 (fill the workbook) –
4.3 rdm generate Checks the workbook, creates the futures, writes the run folder
4.4 rdm run Builds, compiles and solves every future, then collects the CSVs
4.5 (open the results) –
4.6 change, run again –

Step 4.1. Get the interface workbook

python -m ostram --setup unescap_training rdm template --out Interface_OSTRAM_RDM.xlsx

This only writes an Excel file, Interface_OSTRAM_RDM.xlsx, in your OSTRAM folder. rdm template reads the technology and fuel names of the root B_Optimised_VRE from A1_Outputs_B_Optimised_VRE\ (built in step 3.4) to fill the Selector dropdown.

Where the workbook lives. Keep it in your OSTRAM folder, where you run the commands. Each run reads it from there and copies it into its run folder as a record:

Where Written by
Your workbook, the one you edit <your OSTRAM folder>\Interface_OSTRAM_RDM.xlsx you, or rdm template
The run's copy workspace\setups\unescap_training\rdm\<Run_Name>\interface.xlsx rdm generate and rdm run

Always edit your workbook, not the copy. The file name is not the run name: the run name is Run_Name on the Setup sheet (step 4.2).

The template has six sheets (README, Setup, Futures, Future_Changes, Uncertainty_Table, Outputs) and a hidden Lists sheet for the dropdowns. Futures, Future_Changes and Uncertainty_Table come pre-filled with the worked example of step 4.2, from row 2; overwrite or delete it. --blank leaves it out.

Step 4.2. Fill the workbook

Setup

Setting Example What it decides
Run_Name test01 The run folder rdm\test01\
Base_Scenario B_Optimised_VRE The root every future starts from
Samples_Per_Future 1 Sampled variants per named future; 0 means no sampling
Random_Seed 12345 Same seed, same sampled values
Run_Central_Future Y Also run each named future without sampled values
Apply_VRE_Ceilings Auto The shared solar and wind ceilings; the training setup has none
Model_First_Year, Model_Last_Year 2023, 2050 Where a change with an open end starts or stops

Futures

Future_ID Name Run
F00 Baseline Y
F01 Cheap solar Y
F02 High demand, dear coal Y

A future with no changes is the root itself: F00 is the baseline future, the root solved again inside the RDM run, so its results sit in the same CSVs as the other futures.

Future_Changes: what makes each future different

Future_ID Sheet Parameter Selector_Type Selector Operation Value Year_From Year_To
F01 Secondary Techs CapitalCost Tech_Prefix PWRSPV Multiply_Ramp 0.7 2026 2035
F02 Demand_Projection SpecifiedAnnualDemand Fuel_Prefix ELC Multiply 1.15 2027
F02 VariableCost VariableCost Tech MINCOABGD Multiply 2

In words: in F01 the capital cost of every solar plant (PWRSPV…) falls from 100 % in 2026 to 70 % in 2035 and stays there; in F02 electricity demand is 15 % higher from 2027, and Bangladesh's coal price doubles.

Sheet, Selector and Parameter point to cells in the root's model workbooks in preparation\A1_Outputs\A1_Outputs_B_Optimised_VRE\:

Workbook Sheet Holds
A-O_Parametrization.xlsx Secondary Techs power plants, storage, interconnectors (PWR…, TRN…)
Primary Techs fuel supply (MIN…)
Demand Techs the grid tiers between plants and demand
VariableCost fuel prices and other running costs
A-O_Demand.xlsx Demand_Projection electricity demand, one row per demand fuel

A change applies to the rows whose Tech column (on Demand_Projection: Fuel/Tech) matches the Selector and whose Parameter column matches Parameter, in the year columns given. Open these workbooks to find the names to type. They are not the input file OSTRAM_Scenario_Inputs.xlsx, whose sheets have similar names with underscores; RDM never changes that file.

Operations: Multiply, Multiply_Ramp (a straight line from 1 at Year_From to Value at Year_To, held after), Set, and Copy_From_Tech (copy every year from the technology named in Value). Blank years mean every year.

Uncertainty_Table: what is sampled inside every future

X_ID Name Applies_To Sheet Parameter Selector_Type Selector Method Min Max Year_From Year_To
X1 Demand growth ALL Demand_Projection SpecifiedAnnualDemand Fuel_Prefix ELC Multiply_Ramp 0.9 1.1 2026 2050
X2 Gas price ALL VariableCost VariableCost Tech_Prefix MINGAS Multiply 0.8 1.5

Each sample draws one value of X1 and one of X2. Applies_To = ALL layers them inside every future; F01, F02 limits them to those two. Linked_To makes one row move with another.

Outputs. Export = Y puts an input parameter or result variable in the RDM CSVs; the timeslice-level ones are large and N by default.

Save the workbook and close Excel: OSTRAM reads the saved file.

Step 4.3. Preview the futures

python -m ostram --setup unescap_training rdm generate --interface Interface_OSTRAM_RDM.xlsx

Run folder: ...\workspace\setups\unescap_training\rdm\test01
6 future(s) from 3 named future(s), base scenario B_Optimised_VRE: F00, F00_s001, F01, F01_s001, F02, F02_s001

Inside (ostram.rdm.cli → interface.py and design.py), in order:

  1. The workbook is checked: every sheet, every row, all problems listed at once with sheet and row. Whether a technology really exists is checked later, in A3.

  2. The setup is checked: Base_Scenario must be a root of the setup.

  3. The futures are listed: with one sample and Run_Central_Future = Y, each named future becomes itself plus one sample.

    Future Starts from Then applies
    F00 B_Optimised_VRE nothing
    F00_s001 B_Optimised_VRE sample 1 of X1 and X2
    F01 B_Optimised_VRE the solar ramp
    F01_s001 B_Optimised_VRE the solar ramp, then sample 1
    F02 B_Optimised_VRE the demand and coal changes
    F02_s001 B_Optimised_VRE the demand and coal changes, then sample 1

  4. The values are sampled by Latin Hypercube from the seed: each range is cut into N slices and each slice used once. Sample 1 is the same draw in every future, so F01_s001 and F02_s001 differ only by their own changes.

  5. Each row becomes scenario edits, in the format of a derived scenario's scenario.yaml (see scenario edits). F02's demand row:

    - sheet: Demand_Projection
  param: SpecifiedAnnualDemand

Part 5. The South Asia model

The same parts, with these differences:

  • Leave out --setup unescap_training: South Asia is the default. Its files are directly under workspace\ (for example workspace\rdm\<Run_Name>\), its inputs and configuration are the top-level inputs\ and config\, and step 3.3 is not needed.
  • The baseline is the root scenarios plus the 17 decision scenarios; the pipeline page gives the order (solve A_Calibrated_BAU first, then the rest with --a-result-seed).
  • Apply_VRE_Ceilings = Auto applies the shared solar and wind ceilings to every future, so F00 differs from the root by those ceilings.
  • The base-year pin keeps the reviewed 2023–2026 values of the calibrated technologies, even after a Set without years.
  • B2 solves with CPLEX by default; the model is larger, so run --compile-only first.
  • A future built on C_Target_VRE needs a solved A_Calibrated_BAU, passed with --a-result-seed <folder>.

Reference

What a future cannot do

  • Start from another derived scenario: a future starts from a root. Copy that scenario's changes into the future's rows.
  • Change the model's structure (a new country, technology or interconnector): that goes into the baseline (step 3.7).
  • Hold a gross import cap or an interconnector direction overlay.
  • Change CapacityFactor: an edit changes the first row of a technology and parameter, and that parameter has one row per timeslice.

How a workbook row becomes edits

Row Edit(s) in scenario.yaml
Multiply, no years op: multiply, factor
Multiply with years op: multiply, factor, years
Set, no years op: set_flat, value (every year, base years included)
Set with years values: {year: value}
Copy_From_Tech op: copy_from_tech, source_tech
Multiply_Ramp, years a to b, final factor f for each year y after a up to b: multiply by 1 + (f − 1)(y − a)/(b − a); then multiply by f for the years after b
